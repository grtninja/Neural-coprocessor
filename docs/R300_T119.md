# R300 - Starfield coverage and timing instruments (T1.19, lordzaxxon555-art)

One revision, one commit. Everything the T1.19 work brings to 0.3.1, what each part does, where it lives and how
to test it. Prepared 2026-10-13 on top of 0.3.1 (with the R299 / R299c rounds). Contributor:
[lordzaxxon555-art](https://github.com/lordzaxxon555-art), tested on Starfield (RTX 4080 SUPER for the game,
RTX 5060 Ti for the neural stage, 3840x2160).

## Read this first

- **Every part is behind its own `mgpu.ini` key, and every key is absent in the shipped `mgpu.ini`.** With the
  keys absent (or 0) the add-on runs the 0.3.1 code path exactly: no new command is recorded, no lock is taken,
  no log line is written.
- This is how the whole project is built, the author's own features included. It is not a judgement on the
  contributed code. A problem seen with a key on can be told apart from one the build already has (turn the key
  off; if the problem stays, the key is not the cause), and a regression is found in one key and one run.
- The keys are listed, commented out, at the end of `assets/mgpu.ini` under "R300". Remove the `;` to turn one on.
  Every contributed key, from all contributors, is also in [`CONTRIBUTED_KEYS.md`](CONTRIBUTED_KEYS.md).
- With at least one key set, ReShade.log has one `[R300]` line at start that lists every key that is on.
  With none set there is no such line.

everything from one part; `grep "\[R300e5\]"` finds one line. The next free number after this revision is **R301**.

## The parts

### Scene-feature filter - R300b - `SceneHandleSet=1`
- **What:** the DLSS evaluate hook accepts any latched scene feature, not only the newest one created. It counts
  evaluates / taken / copies per handle, and moves the scene handle to a live feature when its own is released.
- **Why:** Starfield creates and releases several DLSS features. When it kept evaluating an older one, the vector
  table and the evaluate-route copy froze and frames were sealed without vectors (stretches of about 600 frames
  in his logs). The add-on's own comment (calibrator.cpp, R135) said this case was handled; it was not.
- **Where:** `src/calibrator.cpp` (hook_evaluate, hook_release, the calibrator report).
- **Limit:** the D3D12 hook only. The D3D11 hook keeps the single-handle test.

### DLSS feature lifecycle - R300f1, R300f2 - `FeatureDiag=1`
- **What:** one `[R300f2]` line per DLSS CreateFeature and ReleaseFeature (400 at most), and `[R300f1]` when the game
  stops evaluating its scene feature while it keeps presenting.
- **Where:** `src/feature_diag.cpp/.hpp`; `src/calibrator.cpp` (after_create, so D3D11 creates are covered too;
  hook_release); one table read per frame in `src/gpu1_context.cpp`.

### Temporal record and policy - R300a1-R300a8 - `TemporalDiag=1` and the policy keys
- **What:** per evaluate, whether the vectors belong to the colour frame, their age and the game frames elapsed;
  slot-stamped jitter. The policy keys: single-step vectors (`TemporalMV=single`), a history reset after K frames
  (`TemporalResetK`), refusing vectors from another frame (`TemporalRequireTuple=1`), the slot jitter delta in
  place of R104's (`JitterSlot=1`, needs `JitterComp=1`).
- **Where:** `src/temporal_diag.cpp/.hpp`; `src/gpu1_context.cpp` (stamps at the vector copy and the seal; the
  consumer's scale, bind and reset).
- **Adapted to 0.3.1:** the scale keeps 0.3.1's frame-generation fraction: k = (single ? 1 : elapsed) x fg_frac.
- `TemporalDiag` only logs. **The policy keys change the picture:** test them one at a time.

### GPU 1 job timing and prefetch - R300e1-R300e6 - `Perf11=1`, `PerfPrefetch=1`
- **What:** per job GPU 1 timing, idle gaps, frame age, the copy-queue split. `PerfPrefetch=1` (needs `Perf11=1`)
  evaluates the frame the copy queue has already armed instead of the newest, so the copy overlaps the evaluate.
- **Where:** `src/perf_diag.cpp/.hpp`; `src/gpu1_context.cpp` (the consume loop, copy-queue arming).
- `Perf11` alone is measurement only. **`PerfPrefetch` changes which frame is evaluated and stays an experiment.**
  First numbers (Starfield, 17 minutes): NR evaluates 20.4 -> 28.2 per second, wall per job 46.7 -> 33.7 ms,
  game fps about the same or slightly higher; NGX p95 29.3 -> 40.1 ms and the `[R87]` alignment changes shape.
  (Measured on the test build, tagged R310-R315 there.)

### Producer cost on GPU 0 - R300g1-R300g6, R300h - `ProducerDiag=1`, `Gpu0Timers=1`
- **What:** CPU time to record the producer's copies, bytes sealed vs evaluated, the producer backlog;
  `Gpu0Timers` adds GPU timestamps around those copies.
- **Where:** `src/producer_diag.cpp/.hpp`, `src/producer_gpu_timers.cpp/.hpp`; `src/gpu1_context.cpp`.
- **`Gpu0Timers` writes timestamp queries into the game's command lists:** compare game fps with it on and off.
  `tests/check_killswitch.py` checks that its initialisation is reachable only behind the key.

### Streamline-tagged vectors - R300c, R300d - `SLTagsMvec=1`, `SLTagsCapture=1|2`
- **What:** R300c - the MotionVectors resource the game declared to Streamline replaces the ranked / calibrator
  source; copy timing is unchanged. R300d - the vector copy is also made at the slSetTag call.
- **Where:** `src/dllmain.cpp`, `src/sl_tags.cpp/.hpp` (the declared state at sl::Resource offset 64),
  `src/gpu1_context.cpp`.
- **Adapted:** the COPY_SOURCE transition and its restore are recorded only around a copy that is actually made;
  a tag whose state is unset (UINT_MAX) is skipped; `SLTagsCapture=1` takes eOnlyValidNow tags only,
  `SLTagsCapture=2` takes every lifecycle (the original behaviour). The `[SLT1]` line keeps its 0.3.1 shape.

### Display - R300j, R300k - `BetterConsoleGuard=1`, `DcompNoFallback=1`
- **R300j:** with BetterConsole.dll loaded, the composition mode is used instead of the bridge window. Three crash
  dumps show BetterConsole aborting inside the bridge window's CreateSwapChainForHwnd. Where `[R273]` refused
  composition, R300j accepts the bus cost to avoid the abort.
- **R300k:** when composition fails, no present chain at all instead of falling back to the bridge window.
- **Where:** `src/gpu1_context.cpp` (the composition decision and the present-chain creation).

### Panel - `PanelAutoHeight=1`, `PanelStats=1`, `PanelPersist=1`, `FrameCap`
- `PanelAutoHeight`: the two boxes use the overlay's height (560 px floor); not when NRScale (R299) sized them.
- `PanelStats` (R300l): game present cadence, derived frame interval, payload GiB/s, vector age. Derived figures,
  labelled as such in the panel.
- `PanelPersist` (R300m): panel and hotkey changes are written back to `mgpu.ini`.
- `FrameCap=N` (20-500): caps the game's present; the panel section appears only with a `FrameCap` line.

## Not merged

- Depth at its own size (T1.14): its lever is in no shipped shader; it belongs with the depth-transport work.
- `DcompOverlayAnyDisplays`: 0.3.1 decides multi-display by detection (`[R273]`); `DcompMultiDisplay=1` accepts always.
- The branch's own `mgpu.ini` (it changed defaults), output name and panel title, `src/mgpu_version.hpp`,
  `tests/check_version.py`.

## How it was checked

- Every changed line of 0.3.1 code reduces to the 0.3.1 expression with the keys absent; every added block is
  behind its key. The shipped `mgpu.ini` gains only comments.
- The log tags were renamed into R300 (101 tags; table above) with no other change to the text.
- Syntax check of every changed file against the CI-pinned headers: no new error against 0.3.1. The four unit
  tests and both scripts pass.
- Run 0 (every key absent) against 0.3.1 in the same scene: expected to read like a 0.3.1 log, with no `R300`
  tag at all.

## How to test a key

One key at a time, at 1 and at 0, in the same scene. 0 must read like Run 0. Post the ReShade.log of each run and
say which key and value it was.
